# Engram V3 — Outcome log

V3 records what happened, then looks up similar resolved outcomes on the next run.

It does **not** train or update a routing policy from those records.

**Live demo:** on [Try](https://engram-cjph.onrender.com/try), **Reject** after a blocked Auth run, then **Run agents** again to see the prior.

## What it adds

Each `python main.py run` appends a compact record to `.engram/outcomes.jsonl`:

- task, service, gate, org, manager override, violations, reviewer counts
- `human_decision`: `pending` | `not_required` | `approved` | `rejected`
- `prior_ids`: resolved similar outcomes that were injected as constraints

A human can close the loop without merging anything:

```bash
python main.py run
python main.py resolve --last --decision rejected --note "ADR-12 stands"
python main.py run
```

The second run should show `prior: … rejected  ADR-12 stands`. Pending outcomes are ignored until a human resolves them.

API: `GET /outcomes`, `GET /outcomes?stats=true`, `POST /outcomes/{id}/resolve`

## Honest bar

- Lookup of past human decisions for similar tasks (same service, similar task text). Not a model.
- Priors are **constraints**, not a gate. ADR-12 still blocks because of the risk rule, not because a previous run was rejected.
- `approved` does not merge the sandbox. It only records that a human said so.
- Counts (`block_rate`, `manager_override_rate`) are descriptive. Do not treat them as a published result.
